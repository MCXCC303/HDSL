# 启动：挑选、校验、注入

> 从点击启动到子进程起来的五步，以及每一步失败时会发生什么。

一次启动由两部分组成：玩家看到的启动对话框（四个可见步骤），和真正按顺序做事的启动计划。下面按实际发生顺序写。

## 挑选账号

顺序是：**实例自己指定的账号 → 账号页上选中的账号 → 列表里的第一个**。

实例点名的账号已经不存在时，不会退而用别的账号，而是按「没有账号」启动并写一条日志。理由很直接：用一个没人选的密钥去启动，比不启动更糟。一个账号都没有时同样按「没有账号」启动。

玩家选中的是**离线账号**时，按[三种账号](01-concepts.md#三种账号)的规则，后面所有注入步骤全部跳过。

## 校验密钥

拿账号的端点问一次 `/models`，这是「需要密钥、又几乎不花钱」的最小请求。

* OpenAI 系协议：地址 `{baseURL}/models`，请求头 `Authorization: Bearer <key>`。
* Anthropic 系协议：地址 `{root}/v1/models`（root 是去掉末尾 `/v1` 的地址），请求头 `x-api-key` 与 `anthropic-version: 2023-06-01`。

两种协议都会带 `Accept: application/json`，以及一个说明「是谁在问」的 `User-Agent`。

然后按回答分三种情况处理：

| 回答 | 结果 |
|---|---|
| 200，返回体确实是一份模型列表 | 通过 |
| HTTP 401 / 403 | **中止启动**，消息里带账号名和供应商自己给的原因，玩家据此就知道该改哪一行 |
| 连不上，或答得不像模型列表（有的主机对任何路径都回 `200 Not Found`） | 照常启动，只记一条日志 |

只有明确的拒绝才会中止启动。今天连不上，一分钟后可能就连上了，不该因为一次*检查*失败就拒绝启动。

> **提示**：这一步是玩家最常看到「启动失败」的地方。插件不必重复做这件事。

## 获取模型

向同一家供应商要模型列表，两种常见形状都认：`{"data":[…]}` 数组，以及 `{"models":{…}}` 字典（字典的键就是模型 id）。

每次启动都问，从不缓存。列表由供应商说了算、且经常变；写死一份只会同时带来两个问题：列出了已经下线的模型，又看不到新来的模型。

取不到时，看账号里有没有写 `model`：

* 写了，就把那一个模型写进路由。它是兜底，不是数据源。
* 没写，**中止启动**，并说明是哪个地址没答上来。

列表为空时不会退化成 `default` 之类的假名字。harness 对不认识的供应商没有目录可查，编出来的模型名只会在启动 harness 时再失败一次，而那次失败信息与玩家真正的问题毫无关系。

## 注入

接下来按顺序做七件事。头两件是收拾上一次，中间四件是这次要留下的东西，最后一件是给玩家的顺带便利。除了第 4、6 件，任何一件失败都只记日志、继续启动：少了它们账号仍然能用，只是少了一处冗余或便利。

1. **补做上一次没做完的回收**：上一次启动如果被强杀，便签还在，这里先按便签把路由收走，顺带还原 `settings.yaml` 里启动器写过的部分，见[回收改了什么](04-exit.md#回收改了什么)。
2. **收走启动器自己的旧路由**：按名单把启动器造过的、且不是本次要写的那条路由从 patch 里取出。玩家自己的供应商不在名单里，永远不碰。
3. **写账号契约**（不含密钥）：进程环境一份，`home/.env` 一份，见[账号契约参考](../plugin-guide/02-account-contract.md)。
4. **写便签与名单**：便签记这次动过哪条路由、写在哪个 profile，名单记启动器造过这个名字。这一步失败会**中止启动**：没有便签就没有回收的依据。
5. **把路由的 `apiKeyEnv` 写一份到旧设置文件**：`settings.yaml` 的历史通道，见下面的说明。
6. **写路由本体**：写进 `profiles/<profile>/cordis.patch.yml`。这一步失败同样**中止启动**：账号交不出去，harness 起来也只会问玩家自己配一个供应商。
7. **写默认模型**：账号里写了 `model`、且不是官方账号时，把它写进 `settings.yaml`，让 harness 开局就用这条路由上的模型。

第 6 步写进 patch 的内容长这样（真实文件）：

```yaml
- id: llm-pi-ai
  name: "@deepseek-ai/dsh-llm-pi-ai"
  config:
    providers:
      MCXCC-sf1:                                    # ← 路由名
        apiKeyEnv: HDSL_LAUNCH_API_KEY_MCXCC_SF1_6DC38953   # ← 只有变量名，没有密钥
        api: openai-completions
        baseURL: https://api.siliconflow.cn/v1
        models:
          - id: zai-org/GLM-5.3
            name: zai-org/GLM-5.3
```

### 写 patch 的三条规矩

启动器自己遵守这三条，插件也应遵守：

* 只动**最后一条** `- id: llm-pi-ai` 条目（harness 的配置编辑器编辑的也是这一条）。
* 只替换 `config.providers.<路由名>` **这一段**，其它行、注释、缩进风格一个字节不改。
* 内容已经一模一样时不写文件，让文件时间戳仍然只表示「人改过」。

> **说明**：第 5、7 步写的 `settings.yaml` 是历史通道。从某个 harness 版本起，harness 启动时只要看到这个文件，就会把它改名成 `settings.yaml.imported`，并把里面的段落合并进 profile 的 patch。所以这两步的最终落点仍然是 patch；它们失败不影响路由可用，只是少了一处冗余记录。插件不要把这个文件当配置源读。

## 子进程环境

启动的进程是 `<实例>/dsh/node_modules/@deepseek-ai/dsh/lib/bin.js`，用实例自己的 Node 运行。环境变量按下面的顺序叠加，**后面的覆盖前面的**：

```text
DSH_HOME               实例的 harness home
HDSL_LAUNCH_API_KEY_…  本次账号的密钥（DeepSeek 路由再加 DEEPSEEK_API_KEY）
PATH                   Node 运行时自带的路径
<实例自定义环境>        玩家在实例设置里填的变量 ← 同名会覆盖上面的密钥
HDSL_ACCOUNT_*         账号契约，最后写，保证描述的是事实
```

> **注意**：第四层由玩家控制。如果玩家自己在实例环境里定义了一个与密钥同名的变量，以玩家的为准。插件读到「没有密钥」时，先想想这条。

## 中途失败

* 进程**没起来**（起不来、工作目录没了）：启动器直接调用一次回收，然后报错。
* 玩家**取消了启动**：取消按钮走的就是停止途径，见[唯一的触发点](04-exit.md#唯一的触发点)。
* 启动计划在写完路由之后、起进程之前失败（少见）：便签还在，**下一次任意启动**会补做回收。

也就是说，路由一旦写出，就一定会被收走。靠的不是每条失败路径都记得清理，而是把回收挂在**子进程退出**和**下一次启动**这两个不会漏掉的事件上。
