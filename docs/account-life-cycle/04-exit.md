# 退出：回收、清理

> 回收挂在子进程退出这一个事件上，便签与名单负责迟做但不漏做。

## 唯一的触发点

回收不是挂在某个「停止」按钮上的，而是挂在**子进程退出**这个事件上：

```text
子进程退出
   └─ DshProcess 的等待线程发现退出
        └─ 状态变为 STOPPED / FAILED
             └─ 进程管理器唯一的那个状态监听器
                  └─ 按便签回收：路由从 patch 取出、settings.yaml 里启动器写过的部分还原
```

这样做的意义是：只要子进程真的退出，回收就一定发生，不管是谁让它退出的。因此所有停止途径都不需要各自记得清理：实例页的「停止」按钮、启动对话框的「取消」、harness 自己崩溃或正常退出、关闭启动器时的关闭钩子，走的都是这条链。

启动失败（进程根本没有起来）是唯一一个例外，它没有监听器可用，由启动器直接调用一次回收。

日志窗口的「终止」按钮值得单独提一句：它用的是 harness 复用的那个日志窗口自带的停止，只杀进程，因此不跑退出后自定义命令、也不清后代进程；但子进程照样退出，所以回收照常发生。

任何一条路径上，回收失败或来不及（例如 JVM 直接被杀死）都不会留下永久残留，见[便签与名单](#便签与名单)。

## 便签与名单

两个小文件让回收「迟做但不漏做」。

* `.hdsl-injected.json` 是**便签**，记着这次动过的路由名、写在哪个 profile、以及时间，是回收时的依据。
* `.hdsl-injected-routes.json` 是**名单**，记着启动器造过的全部路由名（没有密钥），便签丢了也能认出「这是我造的」。

于是三种情况都不会漏：

| 情况 | 结果 |
|---|---|
| 启动器被强杀 | 便签还在，**下一次任意启动**（哪怕用离线账号）会先补做回收 |
| 便签也丢了（很老的版本，或手工删过） | 名单兜底，启动时把名单里、且不是本次要写的路由从 patch 里收走 |
| 正常停止 | 便签在回收过程中被删除 |

## 回收改了什么

* `profiles/<profile>/cordis.patch.yml`：把本次写的 `config.providers.<路由>` **整段取出**，其它字节不动，文件恢复成启动前的样子。
* `settings.yaml` 里的 `llm-pi-ai.providers.<路由>`：启动前没有过就删掉，启动前就有则原样保留（那可能是 harness 或玩家写的）。
* `settings.yaml` 里的 `agent-default-model`：只在它仍然指向本次这条路由时还原。
* 便签：删除。

## 不回收什么

下面这些是故意留下的：

* **名单**：下次还要认自己的旧路由。
* **`home/.env` 里的账号契约**：它是「这个实例以谁的身份运行」的持久说明。
* **玩家自己的路由与玩家对配置的任何其它修改。**
* **「打开终端」生成的脚本**：里面含密钥，需要玩家自己处理。

> **注意**：由此有一条对插件很重要的推论：退出之后，`HDSL_ACCOUNT_ROUTE` 指向的那条路由可能已经不在配置里了。持久保存「路由地址」之类的信息没有意义，每次启动重新读一次才对。
